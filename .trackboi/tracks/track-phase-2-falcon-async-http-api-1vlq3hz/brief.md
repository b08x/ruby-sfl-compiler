## Why Falcon\n\nFalcon is a Ruby async HTTP server built on the `async` gem. Unlike Puma/Unicorn, Falcon's concurrency model is fiber-based — each request runs in its own fiber within an event loop, which is safe for I/O-bound work (LLM API calls, PostgreSQL queries) without multi-threading. This is important because the PyCall constraint bans multi-threaded spaCy use; Falcon's fiber model avoids the problem at the server level (Pass 1 compile requests can be routed to Sidekiq jobs rather than executed inline).\n\n## API surface (from docs/guides/modular-integration.md)\n\n```\nPOST /pipeline/compile        # { text, document_id } → AnnotatedClause[]\nPOST /retrieve                # { query, filters: { min_modality, min_tenor, mood } } → Clause[]\nPOST /synthesize              # { query, filters, limit } → SynthesisResult\nGET  /workflows/:id/status    # → Gush workflow status (for async compile jobs)\nPOST /workflows               # { jsonl_path } → starts ConversationAnalysisWorkflow, returns workflow_id\n```\n\n## Architecture\n\n- Falcon server fronts all endpoints\n- `/pipeline/compile` dispatches a Sidekiq `CompileTurnJob` (async, returns workflow_id) OR runs inline for single-clause requests\n- `/retrieve` and `/synthesize` are fully inline (PostgreSQL + pgvector, no PyCall)\n- Bootstrap wiring reused from `lib/sfl/compiler/bootstrap.rb` — the API server calls `Bootstrap.call` on startup\n\n## Key files\n\n- New: `lib/sfl/compiler/api/` (Falcon app, route handlers)\n- New: `exe/sfl-api` (binstub)\n- `sfl-compiler.gemspec` — add `falcon`, `async` dependencies\n- `lib/sfl/compiler/bootstrap.rb` — extend to support API server init mode\n\n## Relationship to modular-integration.md\n\nThe integration guide already shows the public API surface (Pipeline.compile, HybridRetriever, ContextSynthesizer). The Falcon API wraps these over HTTP so any external RAG pipeline (LangChain, LlamaIndex, etc.) can consume SFL annotation without embedding the gem.
